# BGM JSON — Hierarchical Composition Strategy

This document describes the hierarchical composition strategy used in BGM track files like `title-screen.json`. It is not a mandatory rule — it is a recommended technique whenever a track's repetition pattern benefits from it.

## Context: Music in 4/4

When a track is in **4/4** time (4 beats per measure), the strategy below fits naturally. If the time signature differs, adapt the approach accordingly.

## Strategy: Recursive Prime-Factor Hierarchy (DRY)

The core idea is to build the track **bottom-up** from atomic 2-beat cells, then group them recursively using prime factorization. Any duplicate group across any level is shared by reference — zero repetition.

The hierarchy is **auto-generated** by running:

```bash
bun run src/format-4-beat-music.ts data/audio/bgm/<track>.json
```

### Level 0 — Cells (2-beat atomic patterns)

Reusable 2-beat patterns. In 4/4, two cells fill one measure.

```json
"bass-cgeg": [ ["c4", 0.5], ["g4", 0.5], ["e4", 0.5], ["g4", 0.5] ]
```

Naming convention: `{track}-{note-names}` for readability (the script strips octave digits from the concatenated pitch letters).

### Levels 1+ — Recursive Prime Grouping

All levels above cells are named `{track}-l{level}-i{item}` and are auto-generated.

**Algorithm** — for each level, given N consecutive items:

1. `X = largest_prime_divisor(N)`
2. If `X == N` (N is prime or 1): create a single group containing all items — stop.
3. Otherwise `P = N / X` — split into P groups of X items each.
4. Each group becomes an `l{level}` entry; recurse with the P group names at `level + 1`.

The recursion terminates when only one group remains (the root). A track's `channels.{track}.notes` is then a single-element array: `["{track}-root-key"]`.

### Example — Bass track with 32 cells

```
32 cells
  → X=2, P=16 → 16 groups at l1 (bass-l1-i1 … bass-l1-i16)
  → X=2, P=8  →  8 groups at l2 (bass-l2-i1 … bass-l2-i8)
  → X=2, P=4  →  4 groups at l3 (bass-l3-i1 … bass-l3-i4)
  → X=2, P=2  →  2 groups at l4 (bass-l4-i1, bass-l4-i2)
  → X=2, P=1  →  1 group  at l5 (bass-l5-i1)  ← root
```

Result: 5 levels, all branching in pairs of 2. The root `bass-l5-i1` contains the entire track.

## Flat Dictionary + Track Roots

All phrases (cells + all hierarchy levels) live in a single flat `phrases` object. The script output provides:

- **cells**: leaf-level 2-beat note arrays
- **hierarchy**: all `l{n}` entries (arrays of string references to the level below)
- **track_roots**: mapping `track_name → root_key` — each channel's `notes` array becomes `[root_key]`

## Track Prefix

Every phrase key must be prefixed with the track name (`lead-`, `bass-`, etc.) because the engine merges all phrases into a single lookup table. Without a prefix, different channels could overwrite each other's definitions.

## Channel Structure

```json
{
  "bpm": 120,
  "time-signature": [4, 4],
  "channels": {
    "lead": { "wave": "sine", "volume": 0.5, "notes": ["lead-l5-i1"] },
    "bass": { "wave": "sine", "volume": 0.5, "notes": ["bass-l5-i1"] }
  },
  "phrases": { /* all cells + all hierarchy entries */ }
}
```

Each channel's `notes` references a single root key that expands to the full track.

## Summary

| Principle | Description |
|---|---|
| **DRY hierarchical** | Zero manual repetition. Prime-factor grouping auto-generated by the formatter script. |
| **4/4** | Strategy works naturally in 4/4; 2-beat cells pair into 4-beat measures. |
| **Prefix everything** | `{track}-{name}` to prevent name collisions across channels. |
| **Lower-kebab-case** | JSON keys follow lower-kebab-case (rule R5.2). |
| **Auto-generated** | Run `format-4-beat-music.ts` to regenerate the hierarchy from raw note data. |
